# Сценарий визуализации forward pass

Документ собирается итеративно. Сюда попадает только то, что **обсуждено
и подтверждено**: как часть визуализации соответствует математике модели
Qwen-2.5-3B на промпте «Reaching ATH (».

Принципы:
- Все числа — реальные из forward pass'а, лежат в `public/data/tensors/`.
- Никаких выдуманных данных, никаких метафор-замен — только метафоры-надстройки
  поверх правдивой механики.
- Один непрерывный 3D-кадр, скролл в обе стороны, реверсивный.

---

## Beat 0. Заглавный текст

**Видим:** На старте — текст `Reaching ATH (` крупно, в кадре по центру.

**Математически:** Это и есть промпт, который реально подавался в модель.

**Источник:** `metadata.json` → `prompt`.

**Статус:** ✅ утверждено

## Beat 1. Нарезка на 4 токена через BPE

**Видим:** При скролле текст начинает «трескаться» по границам:
`Re | aching | ATH | (`. Каждый кусочек отъезжает в свою позицию (4 столбца
будущей сцены).

**Математически:** Tokenizer Qwen применяет жадный детерминированный BPE,
получает 4 токена. Это не выбор модели — это фиксированный алгоритм,
заранее заданный словарём merge-правил.

**Источник:** `metadata.json → input_tokens` — реальные `decoded` строки и ID:

| Позиция | Токен | ID |
|--------:|:------|---:|
| 0 | `Re` | 693 |
| 1 | `aching` | 11 829 |
| 2 | `·ATH` | 87 089 |
| 3 | `·(` | 320 |

**Статус:** ✅ утверждено

## Beat 2. Книга-словарь и поиск ID

**Видим:** Под каждым отделившимся токеном раскрывается **книга-словарь**.
По её страницам пробегает поиск (это анимация листания). Скорость листания
зависит от расстояния между ID соседних токенов: ID близки — листает
медленно; ID далеки — листает быстро. На каждой остановке книга открывается
на нужной странице, и из неё «вытягивается» соответствующий ID, который
прикрепляется к токену.

**Математически:** Словарь модели — фиксированный список из 151 936 строк,
встроенный в модель на этапе обучения. Каждый токен имеет ровно один ID.
Поиск детерминированный (это не «выбор» — это lookup).

**Условности:** Реальный BPE собирает токены **снизу вверх** через merge-правила,
а не «ищет» их в словаре сверху вниз. Метафора книги — допустимое упрощение
результата (финальный ID каждого токена действительно соответствует строке
в словаре).

**Источник:** Размер словаря 151 936 — из `manifest.json → config.vocab_size`.
ID — из `input_ids.bin` (4 значения int32).

**Статус:** ✅ утверждено

---

## Beat 3. Из словаря «вытягивается» вектор длины 2048

**Видим:** Когда ID найден, под ним из книги выходит длинный вертикальный
столбик из 2048 точек/полосок — это эмбеддинг токена. Так делается для
каждого из 4 токенов параллельно (или по очереди — артистический выбор).
В итоге в кадре стоят 4 столбика.

**Математически:** Embedding lookup — модель идёт в свою таблицу
**E** (размер 151 936 × 2048) и достаёт строку с номером ID. Получается
вектор длины 2048 — это «значение» токена в высокоразмерном пространстве
модели.

**Источник:** `embedding.bin` — настоящие 4 × 2048 float32 числа.

**Статус:** ✅ утверждено

## Beat 4. Через плиту W_Q (и параллельно W_K, W_V)

**Видим:** Каждый из 4 столбиков «течёт» через большую квадратную плиту.
Плита показана как полупрозрачная сетка с фактурой (имитация миллионов
выученных значений в её ячейках). Из каждой точки входного столбика
бегущие линии расходятся ко всем точкам выходного — «всё со всем
смешивается». На выходе с другой стороны плиты собирается **новый**
столбик длины 2048.

**На самом деле плит ТРИ:** одна большая (W_Q, 2048×2048) и две узких
(W_K и W_V, обе 2048×256). Для каждого токена три параллельных потока.
На выходе:
- Из W_Q — новый столбик длины 2048
- Из W_K — узкий столбик длины 256
- Из W_V — узкий столбик длины 256

**Математически:** Это матричное умножение. Каждое выходное число — это
взвешенная сумма всех 2048 входных чисел; веса берутся из соответствующего
столбца плиты. Плиты **выучены** на этапе тренировки и фиксированы —
свои на каждом из 36 слоёв.

```
y[j] = x[0]·W[0,j] + x[1]·W[1,j] + ... + x[2047]·W[2047,j]
```

Для y[j], j пробегает 0..2047 (для Q) или 0..255 (для K и V).

**Источник:** Сами плиты W_Q, W_K, W_V в этом репо не лежат (это веса модели,
~170 МБ только для проекций × 36 слоёв). В визуализации показываем плиту
как абстрактную фактуру.

**Статус:** ✅ утверждено

## Beat 5. Reshape в головы и пары

**Видим:** Новый Q-столбик длины 2048 «складывается» в **16 рядов по 128
чисел**. Каждый ряд — одна голова. Затем 128 чисел в каждом ряду попарно
слипаются в **64 двумерные метки** (пары). 16 рядов располагаются как
**4×4 квадрат переключателей-циферблатов**, у каждого циферблата за ним
в 3D-глубину уходят его 64 пары.

То же самое **параллельно** делается для K и V, но компактнее: K-столбик
длины 256 → **2 ряда по 128** → каждый ряд → **2 циферблата с 64 парами в
глубину каждый**. То же для V. Получается визуальная асимметрия:
большой блок 4×4 для Q, и два маленьких блока по 2 для K и V.

**Математически:** Reshape — это **переинтерпретация памяти**, никаких
вычислений. Те же числа, по-другому индексированы:
- Q: (4, 2048) → (4, 16, 128)
- K: (4, 256) → (4, 2, 128)
- V: (4, 256) → (4, 2, 128)

«Пары» — это группировка соседних координат: (q[0], q[1]) — пара 0,
(q[2], q[3]) — пара 1, …, (q[126], q[127]) — пара 63. По 64 пары на голову.

**Структурный смысл:** Q даёт 16 параллельных «запросов» (что я ищу), K и V
дают по 2 «представления» (чем я могу быть найден / что я скажу). Это GQA
(Grouped Query Attention) — каждые 8 Q-голов разделяют одну общую пару
(K-головы, V-головы): головы 0–7 → KV-головы 0; головы 8–15 → KV-головы 1.

**Источник:** Размеры зашиты в `manifest.json → config`. Сами числа Q/K/V
в репо не сохранены (промежуточная величина), но они однозначно вычислимы
из embedding'ов и весов.

**Статус:** ✅ утверждено

## Beat 6. RoPE — поворот пар по позициям токенов

(Этот beat пока обсуждаем и пишем со стороны механики; формального утверждения
визуала ещё нет — обсуждение продолжается.)

**Что мы уже знаем (для будущей записи):**
- Циферблат-голова имеет 64 пары координат внутри (показаны как кольца за
  ним в 3D-глубину).
- У каждой пары k своя **частота** θ_k = 10000^(−2k/128).
- Угол поворота для пары k у токена на позиции m равен `m · θ_k`.
- При переходе от одного токена к другому **позиция m растёт на 1**, и каждое
  кольцо поворачивается на свой угол: пара k=0 — большой угол, пара k=63 — почти
  нулевой.
- **Между слоями RoPE-углы НЕ накапливаются.** Они функция только (позиция, пара),
  и одинаковы на всех 36 слоях.
- Что меняется между слоями — это **числовые значения** в Q и K (длины
  пар-векторов), потому что плиты W_Q^(ℓ) и W_K^(ℓ) свои на каждом слое и
  residual stream к моменту слоя ℓ другой.

(Визуализация этого beat — следующая тема разговора.)

**Статус:** 🟡 в обсуждении

## Beat 10. 36-кратное повторение блока — что итерируется

**Что мы уже знаем (для будущей записи):**
- Один блок — это функция (4 × 2048) → (4 × 2048). На вход — residual stream,
  на выход — он же, но с прибавленными дельтами от attention и MLP.
- На каждом из 36 слоёв **операции одинаковы**, **веса разные** (свои
  W_Q, W_K, W_V, W_O, W_g, W_u, W_d, плюс два g-вектора RMSNorm).
- Поэтому: одинаковая последовательность шагов, но разный attention-узор и
  разные дельты.
- Между слоями **residual stream** буквально течёт и накапливает изменения;
  на 36 слое он сильно отличается от того что было на 0-м.
- Что не меняется: формулы RoPE, softmax, причинная маска, размеры тензоров.

(Визуализация — обсудим как «вспышки машинерии вокруг постепенно
эволюционирующих столбиков», но финальное оформление ещё не утверждено.)

**Статус:** 🟡 механика согласована, визуал в обсуждении
